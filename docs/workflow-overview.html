How a project runs, session by session

Four pictures of the way of working the kit installs: how the kit gets into a project and stays current, what one session does from open to close, how a run of tickets can flow without a new session each, and where every kind of context lives. The text of record is WORKFLOW.md; this page is the version you can read on a phone.

1

Installing and refreshing the kit

WORKFLOW.md §12

Start here. Three starting points, one end state. A greenfield project answers a questionnaire; a legacy project gets scanned; a project with an older kit is updated in place. In every case the installer never touches the project's README and prompts on every conflict.

flowchart TD
    S([Project]) --> T{Has code already?}
    T -- "no (greenfield)" --> G1["python install.py target"]
    G1 --> G2["/setup → guided questionnaire"]
    G2 --> G3["CLAUDE.md + settings.json filled<br/>.claude/rules/ and docs/handoff/archive/ scaffolded<br/>WORKFLOW.md declared lines filled"]
    T -- "yes, no kit yet (legacy)" --> L1["python install.py target<br/>merge / diff / skip per file"]
    L1 --> L2["/setup → Existing-Project Scan<br/>drafts CLAUDE.md from real signals"]
    L2 --> G3
    T -- "yes, older kit installed" --> U1["python install.py target<br/>new files created · changed files prompt<br/>retired files reported"]
    U1 --> U2["/setup --refresh<br/>adds missing sections, keeps your edits"]
    U2 --> U3["Move long area bullets into .claude/rules/<br/>/handoff replaces /wrap"]
    U3 --> G3
    G3 --> W([Work: the lifecycle and the context stack below])

2

The session lifecycle

WORKFLOW.md §4

A session is bounded. It opens from a handoff, verifies the repo before trusting the handoff, records every decision the moment it is made, and closes by writing the next handoff or by deliberately not writing one.

flowchart TD
    A([Open the session]) --> B{Live handoff in docs/handoff/?}
    B -- yes --> C[Read the handoff<br/>Mode: dispatch → /next-ticket]
    B -- no --> D[Start from the plan:<br/>next unblocked ticket]
    C --> E[Distrust clause:<br/>git status · git log -1 · run the tests]
    D --> E
    E --> F{Repo and handoff agree?}
    F -- no --> G[Correct the handoff.<br/>The repo is the record.]
    G --> H
    F -- yes --> H[Read the area's rules file in full]
    H --> I[Work on ONE ticket]
    I --> J{Owner ratifies something,<br/>or an open decision appears?}
    J -- decision --> K[Ask, with the alternatives<br/>explained in simple terms]
    K --> L[Write the ratification NOW:<br/>handoff draft or auto-memory]
    L --> I
    J -- no --> M{Where are we?}
    M -- "~40% of the window,<br/>task continues" --> N[Case 1: handoff<br/>for the SAME task]
    M -- "ticket done,<br/>next ticket clear" --> O[Case 2: handoff named<br/>after the NEXT ticket]
    M -- "ticket done,<br/>no successor" --> P[No handoff.<br/>Loose notes to auto-memory]
    M -- not yet --> I
    N --> Q[git mv the consumed handoff<br/>to docs/handoff/archive/]
    O --> Q
    P --> Q
    Q --> T[Save the transcript:<br/>/save-conversation 'ticket implementation']
    T --> R[Stage. Prompt the owner<br/>for the commit message.]
    R --> S([Rotate: new session])
    classDef term stroke-width:1px
    classDef dec stroke-width:1px
    classDef warn stroke-width:1px
    class A,S term
    class B,F,J,M dec
    class G,P warn
    linkStyle default interpolate step

case 1 the task continues

The chat has reached about 40 % of the model's window. The handoff says exactly where the work stopped; a fresh session picks it up with full context.

case 2 done, next is clear

The next ticket in plan order exists. The handoff is named after that ticket, not the one just finished.

no handoff finished, no successor

Archive the handoff this session started from, put any loose fact in auto-memory, stop. Never invent a next session.

3

Two modes: manual and dispatch

WORKFLOW.md §4.1

The lifecycle above runs in one of two modes, and the owner picks: at the close of /plan-interview, in every handoff's Mode: line, or just by asking. In dispatch mode one session hands each ticket to a fresh agent, so every ticket still starts clean, and the owner answers, approves and commits without opening a new session per ticket.

flowchart TD
    A([Dispatcher session: /next-ticket]) --> B[Read the live handoff:<br/>next ticket]
    B --> C{Deps met, not blocked<br/>on the owner, git clean?}
    C -- no --> X([Stop and tell the owner why])
    C -- yes --> D[Start a fresh ticket-agent<br/>with the handoff as its brief]
    D --> E[Phase 1: plan, no writes.<br/>Returns plan + questions]
    E --> F[Dispatcher asks the owner.<br/>Ratifications written NOW]
    F --> G[Phase 2: build and verify]
    G --> H{Risk surface touched?}
    H -- yes --> I[Dispatcher runs /code-review.<br/>Agent fixes the findings]
    I --> J
    H -- no --> J[Agent stages, writes the next<br/>handoff, proposes the message]
    J --> T[Dispatcher saves the agent's<br/>transcript and stages it]
    T --> K[Owner commits and pushes,<br/>replies next]
    K --> L[Dispatcher checks git:<br/>new commit, nothing staged]
    L --> B
    classDef term stroke-width:1px
    classDef dec stroke-width:1px
    classDef warn stroke-width:1px
    class A term
    class C,H dec
    class X warn
    linkStyle default interpolate step

manual one session per ticket

The owner opens each session from the live handoff, exactly as in the lifecycle above. Best for exploratory work or a ticket that needs the owner in the loop throughout.

dispatch one session, an agent per ticket

/next-ticket relays each agent's plan and questions, runs /code-review on risk surfaces, and waits for the owner's commit and "next". Best for a run of well-specified tickets.

stop dispatch pauses

On "stop", at a milestone, when the next ticket is blocked on the owner, after two agent failures, or at the rotation point; the handoff's Mode: line resumes it in a new session.

4

The context stack

WORKFLOW.md §5–§6

Context is kept in layers, each with one job and one home. The always-loaded file stays small; detail loads when a matching file is opened; ticket state travels in the handoff; durable facts live outside the repo; the lossy path, compaction, is last and only fires if a session overruns.

flowchart LR
    subgraph always["Every session, always loaded"]
        CM["CLAUDE.md<br/>pins · constraints · policies<br/>under 200 lines"]
    end
    subgraph demand["Loaded on demand"]
        RU[".claude/rules/area.md<br/>per-area mechanics<br/>paths: frontmatter"]
        WF["WORKFLOW.md · the plan · the spec<br/>read by pointer"]
    end
    subgraph between["Between sessions"]
        HO["docs/handoff/HANDOFF-next-ticket.md<br/>ticket state · verification · ratifications"]
        AR["docs/handoff/archive/<br/>history, never rewritten"]
    end
    subgraph durable["Durable, outside the repo"]
        ME["Auto-memory<br/>facts · preferences · feedback"]
    end
    subgraph history["History"]
        TR["Saved transcripts<br/>/save-conversation"]
        GT["git + tests<br/>the only trusted memory"]
    end
    subgraph fallback["Fallback only"]
        CO["Auto-compaction<br/>autoCompactWindow above the rotation point"]
    end
    CM --> RU
    CM -. "points to" .-> WF
    HO -- "consumed" --> AR
    HO -. "loose facts" .-> ME
    CO -. "only if a session overruns" .-> HO

Two numbers. Rotation at about 40 % of the model's window (≈400K tokens on a 1M model). autoCompactWindow at 500K, above the rotation point, so compaction is the safety net and never the normal path. On a 200K model, lower it to about half that window.
